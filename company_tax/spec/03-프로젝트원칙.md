## 0. 서문

본 문서는 `company_tax` 프로젝트의 **최상위 규범**이다. [요구사항 명세서](02-요구사항명세서.md), [기술 계획서](04-기술계획서.md), [작업 분해서](05-작업분해서.md)는 모두 본 원칙에 종속되며, 본 원칙과 충돌하는 하위 문서의 조항은 무효로 한다.

본 프로젝트는 세무 상담 현장에서 사용되는 계산 도구로서, **계산의 정확성**과 **고객 정보의 보호**라는 두 가지가 타협 불가능한 가치다. 계산이 틀리면 도구의 존재 이유가 사라지고, 정보가 새면 사용자의 직업적 신뢰가 무너진다. 본 원칙의 상당 부분은 이 두 가치를 절차로 강제하기 위해 존재한다.

**원칙의 문언(letter)을 위반하는 것은 원칙의 정신(spirit)을 위반하는 것이다.** "취지는 지켰다"는 주장으로 조항을 우회할 수 없다. 재해석이 필요하면 §6의 개정 절차를 따른다.

## 1. 핵심 원칙

### 제1조 (라이브러리 우선)

> **원칙**: 모든 기능은 UI에 종속되지 않는 독립 모듈로 먼저 구현되고, 화면은 그 모듈을 소비하는 얇은 계층에 머문다.

- 세액 계산 로직은 `calc.js`에 두며 DOM·`window`·브라우저 API를 참조하지 않는다.
- 계산 모듈은 브라우저의 `<script>` 태그와 Node.js의 `require()` **양쪽에서 모두** 로드 가능해야 한다.
- 화면(`index.html`)은 입력 수집·단위 환산·결과 표시만 담당하며, **세액 계산식을 포함하지 않는다.**

> **재해석 근거**: 원 템플릿의 "라이브러리 우선"은 기능을 재사용 가능한 패키지로 분리하라는 취지다. 본 프로젝트는 npm 의존성이 금지된 정적 웹 도구이므로 패키지 배포는 불가능하나, **UI로부터의 로직 분리**라는 본질은 그대로 적용한다.

### 제2조 (실행 가능 인터페이스)

> **원칙**: 모든 계산 모듈은 화면 없이 단독으로 실행·검증할 수 있어야 한다.

- 각 세목 폴더는 `node <폴더>/calc.test.js` 명령 하나로 전체 검증이 완료되어야 한다.
- 검증에 브라우저·개발 서버·빌드 단계가 필요해서는 안 된다.
- 테스트 러너·assert 라이브러리 등 외부 도구 없이 Node.js 내장 기능만으로 실행 가능해야 한다.

> **재해석 근거**: 원 템플릿의 "CLI 인터페이스"는 기능을 사람과 자동화 도구 모두가 호출할 수 있게 하라는 취지다. 본 프로젝트에 사용자용 CLI는 불필요하나, **명령 한 줄로 검증 가능해야 한다**는 본질은 그대로 적용한다.

### 제3조 (테스트 우선 — 협상 불가)

> **원칙**: 실패하는 테스트를 먼저 작성하고, 실패를 확인한 뒤, 그것을 통과시키는 최소한의 코드를 작성한다.

- 계산 로직에 대해 **테스트보다 구현이 먼저 작성되는 것을 금지**한다.
- 테스트는 실행하여 **실패를 눈으로 확인**한 뒤에 구현에 착수한다. 확인하지 않은 실패는 실패가 아니다.
- 기대값은 법정 산식으로 **직접 계산**하여 산출한다. 구현 결과를 실행해 얻은 값을 기대값으로 사용하는 것을 **금지**한다. (구현의 오류가 그대로 기대값이 되어 테스트가 무의미해진다)
- 이 조는 **협상 불가**하다. 일정 압박·단순성·"이미 수동으로 확인함"은 예외 사유가 되지 않는다.

### 제4조 (정보 보호)

> **원칙**: 고객의 자산 정보와 인증정보는 어디에도 남기지 않는다. 남길 곳이 없으면 샐 곳도 없다.

- 사용자 입력값을 `localStorage`·`sessionStorage`·쿠키·IndexedDB 등 **어떠한 저장소에도 저장하지 않는다.**
- 사용자 입력값을 외부로 **전송하지 않는다.** `fetch`·`XMLHttpRequest`·WebSocket·폼 submit을 포함한 일체의 네트워크 전송을 금지한다.
- 소스코드·설정파일·프롬프트·주석에 API 키·계정·접속정보를 **포함하지 않는다.**
- 식별 개인정보(성명·주민등록번호·연락처)는 **입력받지 않는다.**
- 부득이 저장·전송이 필요해지면 기밀정보는 소스와 분리해 환경변수·보안 관리 시스템에 보관하고, 개인정보는 지침에 따라 암호화 저장·복호화 사용한다.

> **"코드에 키가 있다 = 이미 유출된 것으로 간주한다"** — 소스코드 내 인증정보는 형상관리(Git 등)를 통해 외부로 유출될 수 있다.
> **적용 범위**: 소스코드 · 프롬프트 · 설정파일 · 로그 · 화면 출력 · 시스템 간 전송 구간 전체

### 제5조 (접근통제·최소권한)

> **원칙**: 권한 통제 대상 자원이 생기는 즉시, 최소권한·역할기반 통제·인증과 인가의 분리를 적용한다.

- **최소권한**: 업무 수행에 필요한 최소 범위만 부여한다.
- **역할기반(RBAC)**: 개인이 아닌 직무 단위로 권한을 설계한다.
- **인증·인가 분리**: 누구인지 확인한 후, 무엇이 가능한지 판정한다.
- 인증 체계 도입 시 시스템별 개별 인증이 아닌 **전사 통합인증(SSO)** 정책을 따르고, 권한은 직무 기반으로 부여·회수한다.
- **현 적용 상태 (v2.0)**: 🔴 **활성화됨.** v2.0에서 FastAPI 백엔드가 도입되어 아래 활성화 조건 중 "서버 또는 백엔드 API"가 충족되었다. 본 조는 이제 **강제 적용**되며, 다음을 충족하지 않으면 구현에 착수할 수 없다.
  - 사전검토 시스템 접근에 인증을 요구하고, 인증 수단은 사내 SSO 정책을 따른다.
  - 고객 사전정보 조회·보고서 열람 권한을 직무 단위(RBAC)로 설계한다. 담당 FC는 본인이 입력한 상담 건만 조회할 수 있어야 한다.
  - 인증(누구인지)과 인가(무엇이 가능한지)를 분리해 구현한다.
  - GPT API 호출에 사용하는 서비스 계정 토큰은 **최소 권한**으로 발급하고 소스와 분리 보관한다 (제4조·제6조 Don't ③).
- **활성화 조건 (참고 — v2.0에서 이미 충족)**: 다음 중 하나라도 도입되면 본 조가 자동 활성화된다.
  - ✅ 서버 또는 백엔드 API — **v2.0에서 FastAPI 도입으로 충족**
  - 사용자 계정·로그인
  - 사용자 데이터의 영속 저장
  - 다중 사용자 간 데이터 공유

### 제6조 (AI Agent 안전성)

> **원칙**: AI Agent는 사람이 아닌 자동 실행 주체다. 사람과 동일한 권한 체계 안에서만 동작해야 책임 추적이 가능하다.

**현 적용 상태 (v2.0)**: 🔴 **활성화됨.** v2.0에서 GPT API(gpt-4o-mini)를 사용하는 추론 계층이 도입되어 본 조가 강제 적용된다. 아래 Don't 5개 + Must 5개를 **전량** 충족해야 하며, 하나라도 미충족이면 착수·공개할 수 없다.

**v2.0 적용 결정 사항**

| 항목 | 결정 |
|---|---|
| 사용 모델 | **gpt-4o-mini** (승인된 모델 목록에 등재 후 사용 — Don't ①) |
| 개인정보 처리 | 고객 실명·식별정보는 **마스킹·비식별화 후** 전송. 원본은 서버 내에서만 취급 (Don't ②, 제약 C6) |
| 인증정보 | API 키를 소스·프롬프트·프런트엔드에 두지 않음. 서버 측 보안 관리 시스템에 보관하고 최소 권한 토큰만 주입 (Don't ③) |
| 사람 확인 | 사전검토보고서는 **초안**이며, 전문가 검토·승인 없이 고객에게 제공하지 않는다 (Don't ④, Human-in-the-loop) |
| 호출 제한 | 상담 건당 LLM 호출 한도와 차단 정책을 설정 (Don't ⑤) |
| 출력 검증 | 단계별 분리 호출 + 각 단계 **스키마 검증**. 검증 실패 시 재시도·차단 (Must ②, 제약 C8) |
| 로깅 | 프롬프트·도구 호출·결과·비용·오류를 기록 (Must ③, 제11조 연계) |
| 사전 심의 | 공개 전 인젝션·권한 범위·출력 안전성 별도 점검 (Must ⑤) |

**금지 사항 (Don't)**

| # | 금지 | 조치 |
|---|---|---|
| ① | 검증되지 않은 외부 모델·비표준 S/W 임의 사용 | 승인된 모델·표준 S/W 사용, 불가피 시 사전 협의 |
| ② | 외부 모델·API에 개인·민감정보 입력 | 마스킹·비식별화, 내부 모델 우선, 전송 구간 암호화 |
| ③ | 프롬프트·소스코드에 인증정보(API 키) 하드코딩 | 보안 관리 시스템에 보관, 최소 권한 토큰만 주입 |
| ④ | 사람 확인 없이 Agent가 중요 업무 단독 실행 | Human-in-the-loop·Maker-Checker, 실행 범위 사전 정의 |
| ⑤ | 과도한 권한 부여·무제한 외부 호출 허용 | 최소권한으로 범위 한정, 호출 한도(유량제어)·차단 정책 |

**필수 사항 (Must)**

| # | 필수 | 조치 |
|---|---|---|
| ① | 연계 시스템·도구(Tool)·인증 요건 사전 확인 | 대상·인증방식·입출력 규격을 매트릭스로 정리해 검증 |
| ② | 모델 출력 검증·가드레일 적용 | 형식·범위 검증, 프롬프트 인젝션 방어, 이상 응답 차단 |
| ③ | Agent 행위·호출 로그 기록 및 모니터링 | 프롬프트·도구 호출·결과 기록, 비용·오류·이상행위 감시 |
| ④ | SSO·접근통제 등 인증 정책 준수 | Agent별 서비스 계정에 최소 권한 토큰, 직무 기반 회수·갱신 |
| ⑤ | 서비스 오픈 전 보안성·안전성 심의 수행 | 인젝션·권한 범위·출력 안전성을 별도 점검 후 개시 |

> **선례 경고**: 동일 저장소 상위 폴더의 챗봇 위젯(`chatbot-*.js`)은 사용자 API 키를 `sessionStorage`에 평문 저장하고 클라이언트에서 서드파티 엔드포인트로 직접 전송한다. 이는 제4조 및 본 조 Don't ③의 명백한 위반 사례다. **본 프로젝트는 해당 패턴을 답습하지 않는다.**

### 제7조 (단순성)

> **원칙**: 지금 필요한 만큼만 만든다. 영리함보다 명료함이 우선이다.

- **기술 스택은 사내 승인 목록으로 한정한다** (v2.0 개정): Vue.js, FastAPI, Python, FAISS, KURE-v1(fp16), gpt-4o-mini. 목록 외 프레임워크·라이브러리·모델을 임의로 도입하지 않으며, 필요 시 **사유와 후보를 먼저 제시하고 승인**을 받는다 (Agent Don't Rule ①, 제약 C1').
  - *v1.0 원문("프레임워크·빌드 도구 일체 금지")은 정적 계산기 전제의 조항이었다. v2.0에서 서버·RAG·LLM이 도입되면서 해당 전제가 소멸하여, 금지에서 **승인 목록 한정**으로 개정한다. 단순성의 취지는 "승인 목록 안에서도 필요한 최소만 쓴다"로 유지된다.*
- 미래를 위한 가상의 유연성보다 지금 이해 가능한 명확성을 택한다.
- 조기 최적화·조기 일반화를 하지 않는다.
- "코드를 지우는 것"이 최고의 리팩토링이다. 코드 라인 수는 성과가 아니다.

### 제8조 (반추상화)

> **원칙**: 추상화 계층은 그것이 없을 때의 고통이 실재할 때만 추가한다.

- 무거운 의존성보다 무슨 일이 일어나는지 눈으로 볼 수 있는 직접 구현을 선호한다.
- 사용처가 하나뿐인 추상화를 만들지 않는다.
- 세목 계산기 간 공통 코드는 **실제로 중복이 발생한 뒤에** 추출한다. 두 번째 세목 착수 시점에 미리 공통 모듈을 설계하지 않는다.
- 8개 세목 통합([FR-22](02-요구사항명세서.md#34-향후-확장))은 8개가 모두 완성된 뒤 필요성을 재평가한다.

### 제9조 (통합 우선 테스트)

> **원칙**: 단위 테스트보다 실제 사용 경로를 통과하는 테스트를 우선한다.

- 개별 공제 함수의 단위 테스트에 더해, **최종 세액을 산출하는 전체 경로**(입력 → 과세가액 → 공제 → 과세표준 → 세액)를 관통하는 시나리오 테스트를 반드시 포함한다.
- 시나리오 테스트는 **세목당 5개 이상**이며 경계값과 예외 케이스(공제가 재산을 초과하는 경우, 상한·하한에 걸리는 경우)를 포함한다.
- 화면 계층은 자동 테스트 대상이 아니나, 공개 전 **실제 브라우저에서 대표 시나리오의 최종 세액이 자동 테스트 기대값과 일치하는지** 육안 확인한다.

### 제10조 (성능·가용성)

> **원칙**: 기능이 정상이어도 자원이 부족하거나 장비가 멈추면 서비스는 존재하지 않는 것과 같다.

**현 적용 상태 (v2.0)**: 🔴 **활성화됨.** FastAPI 서버 도입으로 아래가 강제 적용된다.

- **성능**: 예상 사용 규모(동시 상담 건수)를 정의하고, 기대 응답속도로 수용 가능한지 검증한다.
  - 세액 계산(Python 코드)은 **1초 이내** 완료되어야 한다.
  - LLM 호출을 포함한 단계별 응답은 사용자에게 진행 상태를 표시하며, 전체 사전검토 1건이 과도하게 지연되지 않도록 단계별 타임아웃을 설정한다.
  - 오픈 전 **부하테스트를 수행**한다 (예상 사용자 규모 기준).
- **가용성**: 단일 장애점을 식별하고 대응한다.
  - **외부 GPT API 장애 시에도 세액 계산 기능은 정상 동작해야 한다.** 세액 계산이 코드로 분리되어 있으므로 LLM 장애가 계산 결과에 영향을 주지 않는다 (제약 C7의 부수 효과).
  - LLM 호출 실패 시 사용자에게 명확히 고지하고, 세액 계산 결과만이라도 제공한다.
  - 서버·인덱스의 백업·복구 체계(RTO·RPO)를 수립한다.
- **업무 중요도 평가**에 따라 서버 이중화 필요 여부를 판정하고, 필요 시 Active-Standby 등 구성 방식을 사전 결정한다.

### 제11조 (관측성·감사추적·사전심의)

> **원칙**: 기록이 없으면 원인 분석도, 사고 추적도, 감사 대응도 불가능하다.

**현 적용 상태 (v2.0)**: 🔴 **활성화됨.** 서버 도입으로 런타임 로깅이 강제 적용된다.

- **런타임 로깅 (신규)**: 다음을 표준 형식으로 기록하고, 위·변조 방지와 보존기간을 적용한다.
  - 사용자 접근·인증 이벤트
  - **LLM 호출 이력** — 프롬프트, 모델명, 도구 호출, 응답, 토큰 사용량·비용, 오류 (제6조 Must ③)
  - 세액 계산 요청·결과
  - 스키마 검증 실패, 이상 응답 차단 이벤트
  - ⚠️ **로그에 고객 실명·식별정보를 평문으로 기록하지 않는다** (제4조 — 적용 범위에 "로그" 명시)
- **감사 추적**: 개발 이력(Git 커밋)도 계속 추적 수단으로 유지한다. 계산 로직 변경 커밋은 테스트 실행 결과를 증거로 남긴다.
- **사전 보안성 심의**: **공개 전** 보안성 점검을 통과해야 한다. v2.0 점검 항목:
  - 제4조 위반 여부 (인증정보 하드코딩, 개인정보 평문 저장·전송·로깅)
  - **프롬프트 인젝션 방어** 및 LLM 출력 안전성 (제6조 Must ⑤)
  - 마스킹 미적용 상태로 외부 API에 전송되는 경로가 없는지
  - 취약점 미조치 상태의 공개를 금지한다.

## 5. 준수 및 우선순위

원칙 간 충돌 시 다음 순서로 우선한다.

1. **제4조 (정보 보호)** — 고객 정보의 보호는 어떤 편의·성능·일정보다 우선한다.
2. **제3조 (테스트 우선)** — 계산의 정확성을 담보하는 절차로, 일정 압박으로 생략할 수 없다.
3. **제6조 (AI Agent 안전성)** — AI 컴포넌트 도입 시 다른 모든 기능 요구사항에 우선한다.
4. **제5조·제10조·제11조** — 활성화 조건 충족 시 즉시 적용된다.
5. **제7조·제8조 (단순성·반추상화)** — 위 조항을 충족하는 범위 내에서 최대한 적용한다.

**제7조(단순성)를 이유로 제3조(테스트)나 제4조(정보 보호)를 생략할 수 없다.** "단순하게 가자"는 테스트를 건너뛰거나 보안 점검을 생략하는 근거가 되지 않는다.

원칙 위반이 발견되면 해당 작업을 중단하고 위반을 해소한 뒤 재개한다. 불가피한 위반은 [기술 계획서 §6 복잡도 추적](04-기술계획서.md)에 사유와 대안 배제 근거를 기록해야 하며, 기록 없는 위반은 허용되지 않는다.
